# `dr`オンデマンド計算実験の判断記録

## 状態

実験は完了しています。技術的にはオンデマンド計算を採用できる見込みですが、このブランチでは本番コードへ統合しません。採用を決定した場合は、別の実装ブランチで移行と再検証を行います。

## 調査した問い

現行アプリは、ダメージダイス数0～202個と`kazanari = 0～9`に対応する`dr`分布を静的JSONとして配信します。この実験では、命中結果から得たダイス数ごとの重みを使い、必要な混合分布1本だけをブラウザ内で計算する方法について、正確さ、応答時間、UIへの影響、実装上の複雑さを調査しました。

## 得られた根拠

最適化実装は、現行JSONに含まれる203ダイス数と10種類の`kazanari`を組み合わせた全2030分布について、最大絶対差約$5.98\times10^{-7}$で一致しました。この差は現行JSONの小数点以下6桁への丸めで説明できる範囲です。命中確率の集約から攻撃力と防御を適用する統合プロトタイプも、`kazanari = 0, 3, 9`で現行経路と最大絶対差$2\times10^{-6}$以内で一致しました。

Windows x64のChrome 150では、最適化実装のメインスレッド中央値が`kazanari = 0`で約0.9 ms、`kazanari = 9`で約44.5 msでした。常駐module Workerを経由した往復時間の増分は中央値で概ね0.1～0.3 msでした。メインスレッド実行では測定回によって`kazanari = 7～9`に50 ms以上のLong Taskが発生しましたが、同じ測定のWorker経路では発生しませんでした。

現行の`dr`アセットは10ファイル、非圧縮約4.02 MiB、gzip圧縮約0.83 MiBです。オンデマンド化によって、この配信量、JSON解析、展開後データの保持を削減できます。一方、読み込み済みJSONを参照する場合より、各入力に対するCPU計算は増えます。

## 暫定的な判断

採用する場合は、`kazanari`や端末性能による切り替え閾値を設けず、すべての計算を単一の常駐module Workerへ送る構成を第一候補とします。`kazanari = 0`でもWorkerの定常的なオーバーヘッドは小さく、非同期API、重複排除、キャッシュ、キャンセル、障害復旧を一つの経路へ統一できます。メインスレッドとWorkerを使い分ける構成は、端末依存の閾値と二重の実行経路を保守する必要があるため採用候補から外します。

ブラウザ内でダイス数別の203分布をすべて再生成する案も採用しません。画面が必要とする混合分布は1本だけであり、全分布の生成は計算量とメモリを不要に増やします。現行JSONを維持する案は、対応環境で性能目標を満たせない場合の有効な代替案として残します。

## 入力範囲と分布範囲に関する判断

オンデマンド化によって受理するダイス数や固定値の範囲を広げる場合は、現在の入力範囲を前提に定めた1024要素の公開結果と2048要素の中間結果をそのまま維持しません。入力範囲、表示可能範囲、中間計算範囲、FFT長を一体として再設計します。ただし、これらを同じ固定長へ拡大するのではなく、それぞれの役割を分離します。

- 表示範囲は、利用者へ個別の確率を提示する値の範囲と、それを超える確率を集約する最終バケットを定めます。
- 中間計算範囲は、技能値、固定値、ダイス軽減などの後続処理を適用しても表示範囲へ戻り得る確率を失わないように定めます。
- FFT長は、対象となる分布の線形畳み込みを循環畳み込みにせず計算できる2の冪として、中間計算範囲から独立に定めます。

判定の達成値は理論上無限の尾部を持つため、入力だけから厳密な最大値を定めず、許容する総打ち切り誤差を先に決め、超過確率がその範囲内に収まる位置まで中間分布を計算します。表示範囲を超える達成値もダメージダイス数へ影響するため、攻撃計算では達成値を表示用の最終バケットへ集約する前に、ダメージダイス数ごとの重みへ変換します。

ダメージロールはダイス数が有限なら有限分布なので、ダメージダイス数、攻撃固定値、防御ダイス、防御固定値から必要な中間範囲を求めます。複数コンボの合計では各分布の範囲を合成します。値ごとの分布を計算する範囲とグラフへ描画する点数は分離し、広い範囲では表示上のビン集約や拡大表示を使って描画負荷を制御します。

固定値を大幅に拡張する場合は、値0から最大値までをゼロ埋めする密配列だけでは扱いません。分布の開始位置を表すオフセットや、互いに離れた確率区間を保持できる疎または区間ベースの中間表現を検討します。警告だけで巨大な配列確保を許可せず、推定計算時間とメモリ使用量による警告範囲と安全上限を設けます。

初回のオンデマンド化と入力範囲拡張は分離します。まず現在の入力範囲で新旧経路の正確性と性能を確認し、その後に範囲決定処理、表示、入力上限を同じ作業単位で拡張します。固定された1024、2048、4096という値を単により大きな固定値へ置き換える方法は採用しません。

## 本番実装へ進む前の未解決事項

- Firefox、Safari、低速なモバイル相当環境で、応答時間、Long Task、メモリ使用量を測定する。
- Viteの本番ビルドとCloudflare Pages配信でmodule WorkerのURLとチャンクが正しく解決されることを確認する。
- 画面入力が連続した場合、複数の計算器を行き来した場合、画面を破棄した場合のWorkerとキャッシュのライフサイクルを決める。
- Workerの生成失敗と計算失敗をUIへどのように表示するか決める。
- 対応端末の性能下限と、最大応答時間およびメモリ使用量の合格基準を先に定める。
- 判定分布の総打ち切り誤差と、複数の計算段階へ誤差予算を配分する方法を決める。
- 入力から表示範囲、中間計算範囲、FFT長、推定計算時間、推定メモリ使用量を求める範囲決定処理を設計する。
- 広い分布をグラフへ表示する際のビン集約、拡大表示、最終バケットの表記を設計する。
