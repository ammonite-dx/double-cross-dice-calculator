# R20: 保守的なグラフ描画レビュー

## 目的

R20では、既存ユーザーが慣れている画面を正本とし、具体的な問題を実測してから必要最小限の変更だけを採用する。計算結果、確率の意味、入力フォーム、画面の順序は変更しない。

先行するR20実験では、PMFの棒グラフ化、upper-tailの階段線、bin集約、threshold抽出、viewport依存の描画、Backtrackの横棒化と確率表などを一度実装した。しかし、これらはユーザーから見える変更であり、現行UIを変更する十分な根拠が実装前に確定していなかったため、`829a628`でR19完了時点の表示へ戻した。先行実験の測定値は、高密度なChart.js描画に問題が生じる可能性を示す探索結果としてのみ保持し、採用する描画方式の根拠にはしない。

## 維持するプロダクト契約

Checkは「入力、グラフ、サマリー」、Attackは「入力、達成値グラフ、ダメージグラフ、サマリー」、Backtrackは「入力、グラフ」の順序を維持する。サマリーや補助情報をグラフより前へ移動しない。

CheckとAttackの確率グラフは折れ線グラフを維持する。通常の表示ではアニメーション、点マーカー、既存の高さ、色、複数系列の比較、表示範囲設定、PMF／upper-tail切替を変更しない。PMFの1座標は`P(X = x)`、upper-tailの1座標は`P(X >= x)`を表すという意味も維持する。

Backtrackは3つのDoughnut chartと既存の配置、色、ラベルの意味を維持する。横棒グラフへの置換、重複するHTML確率表、外部凡例、大きな説明ブロックはR20では追加しない。

## R20で確定している変更

ユーザーが確認するtooltipの意味だけを明確に分ける。PMFは「達成値10」「ダメージ20」のように単一点を示し、upper-tailは「達成値10以上」「ダメージ20以上」のように閾値の意味を示す。確率値とデータ系列名の形式は既存表示を維持する。

チャートには意味のあるaccessible nameを付ける。accessible nameは既存のレイアウトや表示内容を増やさず、同一チャートへ不要な`img`ロールを重ねない。Backtrackにも各Doughnutの役割を識別できる名前を付ける。

## R20で先送りする変更

次の変更は、別途ユーザー上の問題または実測結果を確認するまで実装しない。

- PMFのBar chart化
- upper-tailのstepped line化
- 通常範囲のbin集約やthreshold抽出
- viewport幅に応じた描画点数の変更
- aggregation noticeや表示設定の折り畳み
- Attackの列レイアウト変更
- Backtrackの横棒化、確率表追加、外部凡例
- `animation: false`や`pointRadius: 0`のproduction採用
- `DisplayRangePlanner`のwarning／hard上限変更と`0..20000`の無条件受理

計算コア、CalculationClient、ResourceGuard、RuntimeDamageRollWorker、Worker境界、R17／R18／R19の所有権契約も変更しない。

## 保守的な描画測定

現行のLine chartをそのまま使い、通常のアニメーションと点マーカーを含めて描画負荷を測定する。ケースは100、1,000、4,096、16,384点とし、20,000点は現行policy外の探索ケースとして分けて記録する。Attackの複数コンボを想定して1、2、4系列を測り、390×844と1280×900のviewport、Chrome通常条件とCPU 4x条件を最低限対象とする。

各ケースでChart.jsの初回描画と更新、アニメーション中の応答、Long Task、heartbeatの最大遅延、tooltipの確認しやすさ、ページエラーとコンソールエラーを記録する。markerの半径だけを変えた比較variantを用意してよいが、Lineの種類、色、線幅、データ、チャートサイズ、系列数は変えない。

測定で高密度描画の問題が確認されても、R20ではbin集約やsamplingへ自動移行しない。まずmarkerの小変更と既存の表示資源上限を候補として比較し、それでも解決しない場合は広域描画を独立したプロダクト判断へ送る。改善が確認できなければ「変更なし」を正式な結果とする。

Backtrackの6pxラベルについても、Doughnutを維持した小規模variantだけを実験する。390×844と1280×900で重なり、切り詰め、可読性、カード高さ、3チャートのバランスを比較し、見た目が複雑になる場合は現状を維持する。

## 検証と完了条件

tooltipとaccessible nameの単体・ブラウザ回帰を追加し、graph-firstのDOM順序、既存のDoughnut、既存の入力操作を確認する。R20の完了条件は、確定した最小変更が既存の数値・表示契約を壊さず、測定結果と採否判断がこの文書へ記録されていることである。wide-rangeの新しい描画方式や入力範囲の拡張は、R20完了後の別判断とする。
