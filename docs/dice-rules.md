# ダイスロール仕様

## 文書の位置づけ

この文書は、Double Cross Dice Calculatorが確率分布を計算するときに前提とするダイスロール手順を、実装とテストから参照できる形で定義します。

ルールブックの文章を転載するものではありません。ゲーム内の処理を本アプリ向けに形式化し、事前計算コード、全列挙テスト、乱数シミュレーションの共通仕様として使用します。

現在のステータスは**正規仕様**です。事前計算と独立した全列挙、全生成範囲の数値監査、固定シードの乱数シミュレーション、実行時計算の独立テストによって実装との整合を確認しています。仕様を変更するときは、対応する実装、検証コード、出典情報を同時に更新します。

## 共通定義

- `D10`は、1から10までの整数をそれぞれ確率`1/10`で返す10面ダイスです。
- 同時または追加で振る各ダイスの出目は、互いに独立です。
- ダイス数、クリティカル値、効果の対象数は整数です。
- ダイスを0個振ったときの出目の合計は0とします。
- 出目が同値のダイスは区別しません。効果の対象を選ぶとき、同じ出目の間でどのダイスを選んでも結果が同じなら、同一の事象として扱います。

以下では、`n`個のD10の出目を`X₁, X₂, ..., Xₙ`と表します。

### 効果と変数名

事前計算と実行時計算では、ゲーム内の効果を表現するために次の変数名を使用します。コード上の短い変数名は維持しますが、ルール上の正式名称ではありません。

| 変数・データセット | 主に表現するゲーム内の効果 |
| --- | --- |
| `yousei` | エフェクト《妖精の手》等 |
| `shihai` | エフェクト《支配の領域》と、《絶対支配》による対象ダイス数の増加 |
| `kazanari` | エフェクト《風鳴りの爪》等 |
| `livingdead` | Dロイス《屍人》 |

## ゲーム・アプリ入力domain

次の表が、ゲームルールを表現する入力の正規domainです。ここでいう「固定上限なし」は、任意の大きさを必ず計算できるという意味ではありません。値がJavaScriptの安全な整数で表せない場合や、計算量・メモリ量が安全な範囲を超える場合は、実行前に計算を拒否します。これはゲームのルール制約ではなく、計算資源と数値表現を守るための制約です。

| 入力 | 正規domain | 分類・備考 |
| --- | --- | --- |
| 判定・攻撃・防御のダイス数 | 安全な整数、`>= 0`、固定上限なし | 計算資源の事前判定へ委ねる |
| クリティカル値 | 整数、`2..11` | ゲームルール上の制約。`11`はクリティカルなしを表す |
| 技能値・攻撃固定値・防御固定値 | 安全な整数、固定上下限なし | 負数を含む |
| `yousei` | 安全な整数、`>= 0`、固定上限なし | 《妖精の手》等の最終適用回数 |
| `shihai` | 安全な整数、`>= 0`、固定上限なし | 《支配の領域》《絶対支配》の最終対象数 |
| `kazanari` | 安全な整数、`>= 0`、固定上限なし | 《風鳴りの爪》等の最終振り直し対象数 |
| 難易度 | 安全な整数、`>= 0`、固定上限なし | |
| 残存ロイス数 | 整数、`0..7` | ゲームルール上の絶対上限 |
| Eロイス数 | 安全な整数、`>= 0`、固定上限なし | |
| Backtrackその他減少ダイス・固定値 | 安全な整数、`>= 0`、固定上限なし | |
| 現在侵蝕率 | 安全な整数、固定上限なし | 負値も入力domainでは拒否しない |

`yousei`と`shihai`は同一判定で併用できる場合がありますが、効果を適用する順序によって結果分布が変わり得ます。本アプリは入力モデルを単純に保つため、適用順を追加指定する機能を持たず、両方が0でない入力をサポートしません。これはゲームルール上の禁止でも、計算資源による拒否でもない、現在の対応範囲（supported-feature constraint）です。

## 歴史的な事前計算範囲

次の範囲は、旧フォームと事前計算データを維持していた時期の生成範囲です。ゲーム・アプリ入力domainの上限ではありません。移行履歴を追うために残しますが、新しい実装の入力検証根拠には使用しません。

| データセット | 生成範囲 | 当時の理由 |
| --- | ---: | --- |
| `dx` | 0～99 | 一般判定と攻撃・リアクションの判定ダイス数をフォームが0～99で受理する |
| `dr` | 0～202 | 配列上の最大達成値1023から得る103個に、攻撃力の追加ダイス上限99個を加える |
| `d10` | 0～223 | バックトラックで要求される最大値`3 × 7 + 99 + 99 + 4 = 223`を収容する |
| `livingdead` | 0～223 | 《屍人》で要求される最大値は`3 × 7 + 99 + 99 = 219`だが、バックトラック用データの件数を`d10`と統一する |

`dr`のダイス数は、命中側の配列インデックスを`a`、攻撃力の追加ダイスを`b`として`floor(a / 10) + 1 + b`で求めます。旧実装では`a <= 1023`かつ`b <= 99`だったため、最大値は`floor(1023 / 10) + 1 + 99 = 202`でした。現在はこの値をゲーム上の上限として扱わず、canonical plannerが必要なsupportと資源量を計画します。

バックトラックでは、残存ロイス数を`L`、Eロイス数を`E`、その他減少量のダイス数を`A`、Dロイスによるダイス数補正を`M`として、次の3種類の分布を参照します。

```text
1倍振り: max(0, L + E + A + M)
2倍振り: max(0, 2L + E + A + M)
追加振り: max(0, 3L + E + A + M)
```

旧フォームの上限は`L <= 7`、`E <= 99`、`A <= 99`でした。通常D10を使う選択肢で最大の補正は「戦友(強化)」の`M = 4`なので、追加振りの最大値は223です。《屍人》は他のDロイスと同時に選択しないため`M = 0`であり、`livingdead`を実際に参照する最大値は219です。現在のフォームとcanonical runtimeは、これらをゲーム上の上限として強制せず、JavaScriptの安全な整数とresource policyの範囲で受け付けます。

「戦闘用人格・生きる伝説」の`M = -1`によって補正後の値が0未満になる場合、振れるダイス数は0として扱います。

バックトラック後の最終侵蝕率は、現在侵蝕率から固定値による減少量とダイス合計を引いた値です。通常の1倍振りでは最終侵蝕率を100%以上、71～99%、51～70%、31～50%、30%以下の5区分で表示します。「不死者・悪夢」では120%以上、100～119%、71～99%、51～70%、31～50%、30%以下の6区分で表示します。

2倍振りと追加振りは、通常なら最終侵蝕率99%以下、「不死者・悪夢」なら119%以下を成功として表示します。

| 選択肢 | ダイス数補正 | 使用する分布 | 成功上限 |
| --- | ---: | --- | ---: |
| なし | 0 | 通常D10合計 | 99% |
| 戦闘用人格・生きる伝説 | -1 | 通常D10合計 | 99% |
| 生還者 | +3 | 通常D10合計 | 99% |
| 不死者・悪夢 | 0 | 通常D10合計 | 119% |
| 屍人 | 0 | `livingdead` | 99% |
| 戦友（通常） | +2 | 通常D10合計 | 99% |
| 戦友（強化） | +4 | 通常D10合計 | 99% |

## 通常のD10合計

`n`個のD10を1回ずつ振り、その出目をすべて加算します。

```text
Sₙ = X₁ + X₂ + ... + Xₙ
S₀ = 0
```

事前計算データ`d10`がこの分布に対応します。

## 判定のダイスロール

### 入力

- `n`: 最初に振るダイス数
- `c`: クリティカル値
- `m`: `shihai`。0の場合は通常判定

旧事前計算器が扱った範囲は次のとおりです。現在のruntime calculatorはこの表の上限を入力検証に使用しません。

| 入力 | 範囲 |
| --- | ---: |
| `n` | 0～99 |
| `c` | 2～11 |
| `m` (`shihai`) | 0～19 |

### 通常判定 (`shihai = 0`)

1. 現在のダイスをすべて振ります。
2. `c`以上の出目が1個以上あればクリティカルです。
3. クリティカルした場合は達成値へ10を加え、`c`以上だったダイスだけを振り直します。
4. クリティカルしなかった場合は、そのラウンドの最大の出目を加えて終了します。

したがって、クリティカルが`r`回発生し、最後のラウンドの最大値が`x`だった場合、ダイス部分の達成値は`10r + x`です。

`c = 11`ではD10の出目がクリティカル値に達しないため、追加のロールは発生しません。

`n = 0`はダイスを振らず、自動失敗かつ達成値0として扱います。これはファンブルではありません。

ファンブルとは、振ったダイスの目がすべて1だった場合です。これは最終的なダイス部分の達成値が1の場合と同義です。ファンブル時は技能値を加算せず、アプリ上の達成値を0とします。

### `shihai`（《支配の領域》《絶対支配》）

《支配の領域》は、1回のロールでダイス1個の出目を1へ変更する効果です。《絶対支配》は、《支配の領域》で出目を変更できる対象ダイス数を増やします。

`shihai = m`は、これらの効果を組み合わせた結果として、1回のロールで大きい方から最大`m`個のダイスの出目を1へ変更できることを表します。`m = 0`は効果なし、`m = 1`は《支配の領域》単体に対応し、`m >= 2`は《絶対支配》による対象数の増加を含みます。本アプリでは、次の使用方針を仕様とします。

1. 現在のダイスをすべて振り、クリティカル値以上のダイス数を`k`とします。
2. `k > m`なら、そのラウンドでは効果を使用しません。通常どおり達成値へ10を加え、`k`個すべてを次のラウンドで振り直します。
3. `k <= m`なら、そのラウンドで効果を使用し、大きい方から`m`個を1へ変更して判定を終了します。
4. 現在のダイス数が`m`以下なら、すべての出目が1になり、そのラウンドの最終値は1です。これが最初のダイスロールなら、ダイス部分の達成値も1なのでファンブルです。1回以上クリティカルした後の追加ロールなら、それ以前に加算された10以上の達成値があるため、最終値が1でもファンブルにはなりません。
5. 現在のダイス数が`m`より大きければ、変更後の最大値、すなわち変更前の出目を大きい順に並べたときの`m + 1`番目を最終値とします。

同じ`m`は、効果を使用するまで追加のクリティカルロールにも引き継ぎます。効果を適用して判定を終了した後に、さらに振り直すダイスはありません。

この定義では、`k > m`のときに`m`個だけを1へ変更して`k - m`個を振り直す処理は行いません。クリティカルダイスが`m`個以下になり、効果によってクリティカルを完全に阻止できるラウンドまで使用を待ちます。

### 事前計算上の自動失敗とファンブルの表現

ゲーム上、ダイス0個による自動失敗と、振ったダイスがすべて1だったファンブルは異なる事象です。一方、どちらも技能値を加算しない達成値0として表示するため、事前計算データ`dx`と実行時計算の一部では共通の内部表現を使用します。

実行時計算は値0と値1の確率を合算し、技能値を加算せず、最終的な達成値0へ移します。したがって、ゲーム上の結果とアプリが表示する最終分布は一致しますが、この合算後の確率をそのまま「ファンブル確率」と呼ぶことはできず、`dx`の内部インデックスだけから自動失敗とファンブルを区別することもできません。

最終分布では、自動失敗・ファンブルによる達成値0と、負の技能値を加えた結果として0へ補正された通常の達成値を区別できません。難易度0に対する成功率を正しく求めるため、実行時計算結果は自動失敗とファンブルを合算した`failureProbability`を最終分布とは別に保持します。通常の達成値が技能値補正によって0になった場合は難易度0に成功できますが、自動失敗とファンブルは難易度にかかわらず失敗として扱います。

### `yousei`（《妖精の手》等）

この効果は独立した事前計算データを持たず、`dx`を使って実行時に合成します。

1. 現在のダイス部分の達成値を、10単位で切り上げます。
2. クリティカル値が10以下なら、1個のダイスによる追加の判定結果を加算します。
3. 指定回数だけ同じ処理を繰り返します。

アプリが受理する回数に固定上限はありませんが、計算時間・メモリ量が安全な範囲を超える場合はplannerまたはcalculatorが計算前に拒否します。ダイス数0の自動失敗には適用せず、指定回数にかかわらず達成値0として扱います。現在のアプリは`shihai`との同時使用に対応していません。

### 実行時の達成値と成功判定

自動失敗とファンブル以外の判定では、ダイス部分の達成値へ技能値を加算します。加算結果が0未満なら、アプリ上の達成値は0として扱います。自動失敗とファンブルには技能値を加算せず、達成値0かつ失敗として扱います。

難易度が指定された判定では、達成値が難易度以上なら成功です。ただし、自動失敗とファンブルは難易度0でも失敗します。技能値補正によって通常の達成値が0になった場合は、難易度0に成功できます。

対決ではアクション側の達成値がリアクション側より大きい場合だけアクション側の成功です。同値の場合はリアクション側の勝利として扱います。

## ダメージロール

### 通常のダメージ

ダメージダイスが`n`個なら、通常の結果は`n`個のD10の合計です。

攻撃全体の計算では、命中側の達成値を`a`、追加の攻撃力ダイスを`b`としたとき、ダメージダイス数を次のように決定します。

```text
floor(a / 10) + 1 + b
```

事前計算データ`dr`は、固定値、装甲等による減少、命中失敗の確率を加える前のダメージダイス合計を表します。

アクション側が対決に失敗した場合、最終ダメージは0です。命中した場合、ダメージロールの合計を`R`、攻撃側の固定値を`A`、防御側が振る装甲・ガード・軽減のD10合計を`D`、防御側の固定値を`G`として、最終ダメージを次のように求めます。

```text
max(0, R + A - D - G)
```

実装では途中で0へ丸めて情報を失わないよう、`A - G`が正ならダイス軽減`D`より前に加算し、負ならダイス軽減より後に加算します。

### `kazanari`（《風鳴りの爪》等）

`kazanari = m`は、《風鳴りの爪》等によって、最初のダメージロールの出目が5以下だったダイスのうち、小さい方から最大`m`個を1回だけ振り直す効果を表します。

1. `n`個のD10を振ります。
2. 出目が5以下のダイスを小さい順に並べます。
3. その先頭から`min(m, 出目が5以下のダイス数)`個を選びます。
4. 選んだダイスを取り除き、同じ個数の新しいD10を振って置き換えます。
5. 置き換え後のすべての出目を合計します。

振り直した新しいダイスは、出目が5以下でも再度振り直しません。境界の出目が同じ場合、どのダイスを選んでも合計分布は変わりません。

旧事前計算器が扱った範囲は次のとおりです。現在のruntime calculatorはこの表の上限を入力検証に使用しません。

| 入力 | 範囲 |
| --- | ---: |
| ダメージダイス数 `n` | 0～202 |
| `m` (`kazanari`) | 0～9 |

`n = 0`の結果は0です。`m >= n`でも、出目が6以上のダイスは振り直しません。

## `livingdead`（Dロイス《屍人》）

`livingdead`は、Dロイス《屍人》によって、`n`個のD10のうち最大の出目1個を1へ変更してから、すべての出目を合計する効果を表します。

`n > 0`のとき、結果は次の確率変数です。

```text
Lₙ = X₁ + X₂ + ... + Xₙ - max(X₁, X₂, ..., Xₙ) + 1
```

最大値が複数ある場合も、1へ変更するのはそのうち1個だけです。どの最大値を選んでも結果は変わりません。`n = 0`の結果は0と定義します。

旧事前計算データ`livingdead`がこの分布に対応します。実際に参照していた最大ダイス数は219ですが、生成範囲は`d10`と統一して0～223でした。canonical Backtrack経路では通常D10と《屍人》をruntimeで必要なダイス数まで生成します。

## 配列範囲、上限集約、丸め

旧JSONでは、判定とダメージの中間計算に使用する`dx`と`dr`をインデックス0～2047の長さ2048で生成し、値2047以上の確率をインデックス2047へ集約していました。バックトラック結果を直接表す`d10`と`livingdead`はインデックス0～1023の長さ1024で生成し、値1023以上の確率をインデックス1023へ集約していました。canonical runtimeは要求されたdisplay windowと有限supportを基に配列長を決め、必要な場合だけ互換形式へ投影します。

| 旧データセット | 配列長 | 最終バケット |
| --- | ---: | --- |
| `dx` | 2048 | 2047以上 |
| `dr` | 2048 | 2047以上 |
| `d10` | 1024 | 1023以上 |
| `livingdead` | 1024 | 1023以上 |

旧画面経路では判定・ダメージ・バックトラックの分布を1024要素へ統一し、値1023以上をインデックス1023へ集約していました。現在のcanonical画面経路では、display windowの点数とresource policyを分離し、値を固定1024バケットへ自動的に押し込みません。2048要素の中間表現を使う旧経路の近似と、canonical結果から互換形式へ投影する境界は[`ADR 0001`](./adr/0001-expanded-working-distributions.md)に記載します。

生成物は各確率を小数点以下6桁へ丸めます。すべてのデータセットで、丸め後の確率総和が1になるよう、丸め単位`0.000001`で補正します。

生成時の構造検証では、すべての分布について総和と1の差が`0.0002`未満であることを要求します。

## 検証要件

### 全列挙

少なくともダイス数0～4について、取り得る全出目を列挙して次を比較します。

- 通常D10合計
- すべてのクリティカル値に対する判定
- 有効な`shihai`との組み合わせ
- 有効な`kazanari`との組み合わせ
- `livingdead`

全列挙側は事前計算の数式や中間関数を再利用せず、この文書の手順を直接実装します。

### 乱数シミュレーション

事前計算と独立した単純なダイスロール実装を用意し、固定した乱数シードで代表値と境界値を検証します。低確率の階級は統合し、期待度数が十分な階級に対する適合度検定と、累積分布の最大差を併用します。

試行回数、代表ケース、棄却水準、多重検定の補正方法は[`precomputation-validation.md`](./precomputation-validation.md)に定義します。

### 実行時計算

技能値、自動失敗とファンブル、成功判定、ダメージ軽減、バックトラック区分など、事前計算済み分布へJavaScriptで加える処理は[`runtime-calculation-algorithms.md`](./runtime-calculation-algorithms.md)に記載し、旧Calculatorを参照しない独立テストで検証します。対象ケース、期待値の作り方、実行方法は[`runtime-rule-validation.md`](./runtime-rule-validation.md)に定義します。

### 全入力範囲の数値監査

生成器が受理する全入力について、少なくとも次を確認します。

- すべての確率が有限であり、許容誤差を超えて負にならない
- 上限集約後の確率総和が許容範囲内にある
- 理論上到達不能な値の確率が0である
- ダイス数0、最小値、最大値などの境界条件を満たす
- 6桁へ丸める前後の誤差が定めた上限以内にある
- 同じ入力から同じJSONとマニフェストを生成できる
