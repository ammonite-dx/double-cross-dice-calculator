# ADR 0001: 中間確率分布を2048要素へ拡張する

- 状態: 採用
- 決定日: 2026-07-30

## 背景

公開結果はインデックス0から1023の1024要素で表し、インデックス1023を値1023以上の集約バケットとして扱ってきました。この表現を計算途中にも使用すると、1023以上へ一度集約した値へ負の固定値やダイス軽減を適用したときに、集約前の値を復元できず正しい位置へ移動できません。また、入力範囲で認めている1024以上のシフトに対して配列長が変化する不具合もありました。

DXの達成値は理論上無限に続くため、有限配列だけで全入力を完全に厳密化することはできません。必要なのは、公開結果の意味を維持しながら、現在の入力範囲で最終結果へ戻り得る中間値を失わない十分な作業領域です。

## 決定

公開結果の長さは1024のままとし、`dx`と`dr`の事前計算データおよび判定・ダメージの中間計算には2048要素を使用します。`d10`と`livingdead`はバックトラックの公開結果を直接表すため1024要素のままとします。

判定では2048要素の`dx`へ《妖精の手》と技能値を適用してから1024要素へ集約します。現在の最小技能値-999を適用した場合、2047以上の中間値は1048以上にしかならないため、作業領域の最終バケットを公開結果の最終バケットへ安全に集約できます。

ダメージでは2048要素の`dr`へ固定値差と最大99D10の軽減を適用してから1024要素へ集約します。正の固定値差によって2047以上へ到達した値は、その後に最大990を減算しても1057以上であり、公開結果では必ず最終バケットへ入るため、最終的な1024要素について安全です。

スコアからダメージダイス数を決める境界では、公開スコアのインデックス1023を使用する現行仕様を維持します。1023を超える個別の達成値をダメージ計算まで伝播する完全拡張はこの決定に含めません。

## 影響

事前計算データはschema v2とし、各アセットが個別の`distributionSize`を持ち、マニフェストがデータセット別の`distributionSizes`を記録します。FFTは入力配列長から変換長を決め、1024要素と2048要素の両方を処理します。`dr`の転置キャッシュはメモリ使用量を制限するため最大3種類のLRUとします。

マニフェストを含む配信データ全体は11,272,366バイトから11,984,253バイトへ増加し、増加率は約6.3%でした。ファイル単位で圧縮した合計はgzipで2,361,611バイトから2,475,075バイトへ約4.8%、Brotliで1,590,394バイトから1,659,943バイトへ約4.4%増加しました。全32アセットの生成時間は約30秒でした。

同じ開発環境で変更前後を計測した結果は次のとおりです。2048化で配列は大きくなりましたが、FFTを再帰型から反復型へ変更した効果が上回り、畳み込みを多用する処理は短縮しました。

| 処理 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 通常の`getScore` | 0.013 ms | 0.022 ms |
| `yousei = 9`の`getScore` | 26.730 ms | 3.092 ms |
| 通常の`getDamage` | 3.597 ms | 0.396 ms |
| 10コンボの`getTotalDamage` | 30.613 ms | 1.146 ms |

変更後の値は`scripts/benchmark-calculators.mjs`を3回実行した中央値です。絶対時間は実行環境に依存するため、回帰検出では同じ環境の相対比較を使用します。

## 採用しなかった案

すべての工程を拡張して達成値1023以上をダメージダイス数へ伝播する案では、`dr`を最大304ダイス程度まで増やし、ダメージの作業領域を4096要素へ拡張する必要があります。試作では`dr`のrawサイズが約2.12倍、gzipサイズが約1.92倍となり、実装とメモリ管理も複雑になるため採用しませんでした。

R2や外部ワーカーへ計算を移す案は、Cloudflare Pages上の静的サイトとして完結させる方針と一致しないため採用しませんでした。

## 後続事項

最終バケットへ入る確率が無視できない入力を利用者へ示す表示は別変更として検討します。全工程の拡張が必要になった場合は、有限配列の大きさだけでなく、DXの無限尾部をどの確率誤差で打ち切るかを新しいADRで定義します。
