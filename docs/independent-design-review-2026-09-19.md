実装者の技術力や変更当時の事情は、現在のコードだけから断定できない。本書でいう負債は、現在の保守費用と機能上の必要性の釣り合いに関する評価である。

## 主要な改善項目

優先度Aは公開・継続開発の前に優先したい項目、Bは構造改善として次に扱う項目、Cは測定または製品方針を決めてから扱う項目を表す。障害の深刻度を示すものではない。

### 1. 型検査が実装全体の契約を保証していない — A

根拠: `tsconfig.json:7`の`checkJs: false`、`src/runtime/CalculationClient.js`と`CalculationClientTypes.ts`、`tests/typecheck/calculation-contracts.ts`、Vue UI各ファイル。

型の導入は進んでいるが、計算とruntimeの中心はJavaScriptのままで、47個のVue SFCにも`lang="ts"`がない。JSDocによって呼び出し側の型情報が得られる箇所はあるものの、JavaScript実装内部の整合性を型検査する設定ではない。型テストにある`declare const client: CalculationClient`はインターフェースの使い方を検査するもので、その実装がインターフェースどおりの値を返すことまで保証しない。

UIの`defineProps(['side', 'params'])`や`type: Object`も、ドメイン型からテンプレートまでの接続を弱くする。新しい入力や結果フィールドを加えたとき、型、JSDoc、runtime validator、テストfixture、Vue propsを別々に更新する必要がある。

**提案:** 数値結果型、計算入口、Worker protocol、feature controller、Vue props/emitsの順で、実装自身をTypeScriptで検査する。入口の型を明示して返却実装も検査し、`script setup lang="ts"`でUIまでつなぐ。移行中のJavaScriptには範囲を絞った`checkJs`も選べる。単なる拡張子変更で完了とせず、入力・結果を誤って接続するとビルド前に失敗することを確認する。

Vue公式もSFCの型検査に`vue-tsc`、props/emitsの型付けにTypeScriptを用意している。現在採用済みの道具を最後まで活用する改善であり、新しい基盤の導入ではない。[VueのTypeScriptガイド](https://vuejs.org/guide/typescript/overview)、[Composition APIの型付け](https://vuejs.org/guide/typescript/composition-api)

### 2. レイヤーの制約が共通契約の重複を生んでいる — A

根拠: `src/shared/presentation/DistributionProjectionTypes.ts:12`、`src/domain/CertifiedValue.ts`、`src/calculation/DistributionResultTypes.ts`、`eslint.config.js:95`付近。

表示層はdomain/calculationへ依存しないという方針のため、`CertifiedValue`、support、overflow、分布結果に相当する構造型を表示層でも定義している。コメントも、その再定義がレイヤー方針に由来することを明記している。一方、表示処理は`DistributionResult.js`のruntime validatorを実際に呼んでいる。

結果として、「同じ分布を読む層」が契約だけを共有できず、契約の変更点が増えている。型のみの依存と、計算処理を実行する依存を同一視した制限は、このアプリでは逆効果である。

**提案:** フレームワーク非依存の共有契約を一箇所に置き、engine/runtime/presentationから`import type`する。禁止すべきなのは計算からUIへの依存や参照データの本番混入であり、表示層が結果型を知ることではない。共有契約を変更したとき、利用箇所すべてに型エラーが出る構成が望ましい。

`core/`、`calculation/`、`domain/`、`shared/presentation/`の現在の分割にも説明はあるが、「この型の所有者はどこか」に対して直感的でない。ディレクトリ名を増やすより、契約の所有者を一本化する方が効果的である。

### 3. UIテストの一部が挙動ではなくソース表記を固定している — A

根拠: `tests/checkFeatureArchitecture.test.js:21`、同`:61`、`tests/advancedSettingControls.test.js:17`。

前者は特定のimport文字列やルーターの一行表記を要求し、後者は`v-checkbox-btn`の属性順とclassまで正規表現で一致させる。このため、同じ挙動を保つ整理でもテスト変更が必要になる。特に高度な設定のテストは、現在ラベルの関連付けがないcheckboxの形を固定しており、アクセシビリティを改善するとそのままでは失敗する。

ファイル読み取りを含むテストは31ファイルある。ただし、それらすべてが無価値なのではない。参照資産の本番混入禁止、依存の方向、生成物の契約など、静的検査に適した要件も含まれている。

**提案:** 依存関係の制約はimport graphまたはlintで、UIの要件は描画されたrole・label・操作結果で検査する。移行時の旧パス不在検査は、今後も防ぐべき理由があるものだけ残す。数値オラクル、質量・単調性・tail境界、キャンセルの挙動テストは維持する。

合格基準は「importを別名にしてもテストが壊れず、ボタンの名前や振る舞いを壊したらテストが落ちる」である。

### 4. 操作とグラフのアクセシビリティが不十分 — A

根拠: `src/layouts/AppBarArea.vue:3`、`src/features/attack/ui/InputForm.vue:55`、`src/features/check/ui/ScoreForm.vue:86`、`src/shared/chart/ProbabilityLineChart.vue:52`、`src/features/backtrack/ui/FinalEncroachmentChart.vue:31`。

実画面のアクセシビリティツリーで、ナビゲーションボタン、高度な設定checkbox、狭い表示でのコンボの開閉・複製・削除に名前がないことを確認した。ボタン内の文言を`hidden-sm-and-down`で隠すと、アイコンだけが残る。画面に「高度な設定」と書かれていても、隣のcheckboxと関連付いていない。

グラフには名前が付いているが、それだけでは確率の数値を取得できない。判定と攻撃には一部のサマリーがあるものの、分布そのものの代替表はなく、バックトラックは三つのcanvasが結果表示の中心である。

**提案:** 操作に常時有効な名前を付け、checkboxのラベルを関連付ける。開閉には展開状態を伝える。グラフと同じデータから、確率表や主要値のテキストを提供する。少なくともバックトラックの各選択肢は、成功率を表として比較できるようにする。

これはデザインの好みではなく、データと操作へ到達できるかの問題である。Chart.js公式もcanvasの内容に代替情報が必要であることを説明している。[Chart.js Accessibility](https://www.chartjs.org/docs/latest/general/accessibility.html)

### 5. 「分布を描く」ことが「判断する」ことより前に来るUI — B

根拠: `src/features/check/ui/CheckPage.vue:40`、`src/features/attack/ui/AttackPage.vue:53`、`src/features/backtrack/ui/FinalEncroachmentChartPanel.vue:26`。判定とバックトラックの390px幅での実表示も確認した。

判定・攻撃は、入力、グラフ、サマリーの順に並ぶ。スマートフォン幅では成功率・命中率・期待値に到達するまでグラフと表示設定を通過する。バックトラックは小さいドーナツを二列に置くため、セクター内の数値が小さく、選択肢同士の比較にも視線の往復が必要になる。

カードやVuetifyが問題なのではない。主目的がキャラクター作成やセッション中の判断補助なら、現在の情報の順番が目的に十分合っていない。

**提案:** 同じ計算機能のまま、入力の直後に成功率・命中率・期待値を置き、その下に分布と詳細設定を置く。バックトラックは振り方を行にした比較表を主表示にし、グラフは補助にする。PMFは離散値であることが伝わる描画、上側確率は閾値として読める表現を選ぶ。点数が多いときはマーカーや目盛りを間引いても、確率の意味を変える集約はしない。

追加ダメージ閾値の入力、共有URL、保存プリセットは有望だが、機能追加に当たる。本レビューの構造改善に自動的に含めない。

### 6. 詳細設定の表示状態が計算条件を変更している — B

根拠: `src/features/check/ui/ScoreForm.vue:72`、`src/features/attack/ui/AttackForm.vue:66`、`src/features/attack/ui/DefenceForm.vue:58`。

「高度な設定」を閉じると、妖精の手・支配の領域、攻撃側では風鳴りの爪も0へ戻る。したがってこれは単なる詳細表示の開閉ではなく、効果を無効化する操作である。`showDetails`という状態名と、計算結果へ及ぼす作用が一致していない。

**提案:** 詳細の開閉と、効果の有効・無効を分ける。開閉だけなら入力を保持し、閉じた状態でも「特殊効果2件」のように有効な条件を表示する。効果全体を無効にする機能が意図なら、その操作名を明示する。

同じ観点で、各画面の入力はfeatureのローカル状態にあり、現行コードには入力のURL化・永続保存・`KeepAlive`がない。画面移動後も入力を保持するかは製品方針として決めたい。入力保持の追加は有用だが、公開のために大きな状態管理ライブラリを必須にする理由にはならない。

### 7. 計算・表示の状態管理と内部検証が厚くなっている — B

根拠: `src/features/attack/model/AttackRunner.js:49`、`src/features/check/model/useCheck.ts`、`src/runtime/CalculationFeedback.js`、`src/shared/presentation/DisplayRangePlanner.js:83`、`src/calculation/DamageAggregation.js`。

Attack runnerは、要求世代、表示世代、score表示世代、複数のlast結果、結果保持フラグ、score再計算フラグ、表示エラーフラグを別々に持つ。それぞれに必要な理由はあるが、どの組み合わせが有効なのかは処理全体を読まないと分からない。Checkも初期計算を`await`する経路と、その後のrunner経路を持ち、Attack/Backtrackとライフサイクルが異なる。

また、表示層は内部の表示契約について、独自エラー体系やown-property descriptorの検査まで持つ。合計ダメージの実装には数学的処理だけでなく、入力検証、計画の真正性管理、資源見積り、metadata構築まで集まっている。単に「長いファイルだから分割する」問題ではなく、読者が同時に理解する責務が多い。

**提案:** 入力snapshotと計算結果を対応付けたrecordを基準にし、計算状態と表示状態を別々のdiscriminated unionで表す。`idle / running / ready / rejected / failed`などから有効な遷移を読めるようにする。共通化するのはlatest-winsと破棄処理までとし、機能差を大量のcallbackで吸収する巨大な共通controllerは作らない。

検証はUI入力、外部からの復元データ、Worker message、公開する計算APIなどの入口と、計算出力の数値不変条件に集中させる。内部で自ら生成したDTOまで外部データと同じように扱う必要があるかを見直す。ただしTypeScriptは実行時の防御にならず、typed arrayの`readonly`も実際の書き換えを防がない。コピー・検証を削る前に所有権を決めることが前提である。

### 8. 数値処理の表現と下位実装に整理可能な残存物がある — B

根拠: `src/calculation/ScoreCalculator.js:56`と`:97`、`src/core/probability/FFT.js:71`、`src/calculation/RuntimeDamageRollFFT.js:1`、`src/calculation/planning/RangePolicy.js:35`。

Scoreでは`Float64Array`を`Array.from`で通常配列に変換し、その後`Float64Array`の結果を作る。疎な旧形式を受け入れる分岐もあり、現在の本番DX providerだけを読む場合には必要以上の表現を追うことになる。さらに、range planがない場合は例外にした直後に、planがない場合を想定した`dxOptions`の分岐が残る。

FFTにはcore版とDR版の似たradix-2変換があり、Abortチェックなどに差がある。アルゴリズムの修正を二箇所で管理する理由が、モジュール構造からは十分明らかでない。廃止済みpolicy名を個別に拒否するコードも、本番の正規化処理に残っている。

**提案:** 本番の内部表現を原則として`Float64Array`と明示したtail/offsetに揃える。互換入力は必要な境界のadapterへ移す。到達不能分岐は削除し、policyは許可する項目を中心に定義する。FFTは共通kernelと用途別wrapperへの整理を、数値テストと性能比較の後に判断する。

末尾sentinelの使用自体を不具合とは評価しない。現在は内部のworking distributionと外部の結果契約を区別して扱っている。ただしゼロからなら、内部型でも「この末尾は値なのかtailなのか」が読める形にし、単なる配列長の約束へ依存する箇所を減らす。

この項目は保守性に基づく提案であり、配列変換やFFT重複が現時点の主要な処理時間を占めると実測したわけではない。

### 9. 現行説明と歴史資料の境界が、開発者の入口ではまだ弱い — A/B

根拠: `README.md:15`と`:48`、`package.json`、`experiments/README.md`、`experiments/r22-numerical-performance/node-benchmark.mjs:472`。

初めて読むREADMEに`canonical full-tail`、`published-bucket`、`R25-J`など、移行の文脈を知らないと理解しづらい語が出てくる。特にfull-tailは、無限分布を無限個の値として計算している意味ではなく、実装は有限の明示範囲とtailの証明情報を組み合わせている。初参加者には、その現在の意味を先に説明した方がよい。

実験は現行監査と履歴に分類されているものの、package scriptsには`r22`や`phase2h`といった作業段階名が残る。一部の履歴実験は通常テストからも検査される。測定ツールが追跡中の`baseline-node.json`を固定パスで上書きすることも、初めての再測定時に意図しない差分を生みやすい。

**提案:** READMEは用途、画面例、起動、テスト、コードの読み順を中心にする。「機能を追加するならどこを触るか」を一つの具体例で示す。現行benchmarkは目的名にし、履歴実験は通常の品質検証から切り離す。計算の独立オラクルは履歴とは別に維持する。測定結果は明示した出力先へ保存し、基準値の更新を別操作にする。

履歴と参照JSONを一律に削除する必要はない。再現に使うもの、根拠として読むだけのもの、現在も実行するものを分ければよい。通常の開発にPythonが不要な現在のCI分離は維持する。

### 10. 公開準備として利用条件と窓口の確定が残る — A

根拠: `README.md:117`、`SECURITY.md`、`package.json`、`src/components/Home/NewsPanel.vue`。

READMEにはソースコードのライセンスが整理中と書かれている。公開後の開発参加や再利用を期待するなら、利用条件が未確定なままでは参加者が判断できない。リポジトリの公開と、オープンソースとしての提供は別の判断として整理すべきである。

`SECURITY.md`も、非公開報告機能が使えない場合の具体的な報告先は未確定である。サイトのお知らせは2024年まで、package versionは`0.0.0`であり、いずれも単独で誤りではないが、公開時には「どの版について報告すればよいか」を分かるようにしたい。

**提案:** 所有者がコードのライセンス方針を確定し、ロゴ・画像・ゲーム由来の名称等の扱いと区別して記載する。具体的な報告窓口と、リリースまたはビルドを識別する方法を用意する。本レビューではライセンスを選択・付与していない。

| 通常DX | 1個のCDFから最大値の分布を求める。`log1p`/`expm1`を利用 | 選ぶ | CDF/survival関数とtail計算を小さなAPIとして明確にする。シミュレーションへ戻さない。 |
| 支配の領域 | クリティカル個数を状態にするDP | 選ぶ | 遷移の意味、計算量、使用メモリを隣接文書で説明する。大入力の代替手法は測定後に検討する。 |
| 妖精の手 | 連続クリティカル数の分布の合成とtailモデル | 選ぶ | 特殊効果の数学モデルと、分布生成・certificate生成の対応を追いやすくする。 |
| 通常D10和 | 前向きDPで複数ダイス数の分布を生成 | 小～中入力では選ぶ | 同じ有限supportを返すrolling-sum方式や、大入力での多項式累乗と比較できる。ただし現在の10面ループを置き換える優先度は低い。 |
| DR・風鳴りの爪 | 混合分布の多項式評価、正規化微分、FFT | 選ぶ | 特殊効果なしとありの導出を、最小の例と計算量で説明する。FFTの自作自体を負債と決めつけない。 |
| 命中後ダメージ | 達成値ごとの命中重みをDRに混合し、防御軽減を合成 | 選ぶ | 数学モデル、配列計算、計画・資源管理を別の責務にする。 |
| 複数攻撃の合計 | 畳み込み、tailと期待値区間の伝播 | 選ぶ | 集約の算術、計画、出力metadataを分離し、計算recordの所有権を一貫させる。 |
| バックトラック | 有限supportのDPと区分集計 | 選ぶ | ゲームルールによる区分と表示文言を分け、比較表を主表示にする。 |

`exact`や`bounded`はゲーム上の分布を有限範囲で扱う際の意味論上の確度と、浮動小数点計算の数値診断を区別して読む必要がある。現在の契約はこの分離を意図している。certificateを減らして見かけ上コードを簡単にすることは、無限tailの情報を失わせるため勧めない。一方、これらを計算機算術まで含む形式的な区間証明と誤解しない説明は維持・強化したい。

効率改善は「どの入力を何msで扱いたいか」を決めてから行う。今回新しい全域benchmarkは実行しておらず、一般入力での性能不良は確認していない。既存ADRの代表入力で問題がなかった事実と、現在受け入れるすべての入力が低性能端末でも軽いことは同義ではない。

メインスレッド上の同期処理にAbortチェックがあっても、その処理中にイベントループが新しい入力イベントを処理できるわけではない。これは即座に全計算をWorkerへ移す理由ではなく、今後入力範囲を広げる際に、計算時間と入力応答時間を別々に測るべき理由である。既存のDR Workerを維持し、重い受理ケースが実測で現れたら、その処理をWorkerへ移すか適切にyieldする。最初からWorker poolやWASMを導入する必要はない。

## ゼロから作る場合の構成案

ディレクトリ数を最小にするより、「契約」「数学」「実行」「画面」を明確にする。

```text
src/
  app/                 起動、router、layout、依存の組立て
  domain/              ルール、入力、確率結果の共有型
  engine/
    probability/       分布操作、FFT、tailの基本計算
    score/             DXと達成値
    damage/            DR、命中、軽減、複数攻撃の合計
    backtrack/         侵蝕率の分布と区分
    planning/          必要範囲と資源見積り
  runtime/             非同期実行、cache、Worker、キャンセル
  features/
    check/             page、フォーム、controller、表示変換
    attack/
    backtrack/
  ui/                  共通入力、chart adapter、表示書式
tests/
  unit/                数値オラクル、ルール、分布の不変条件
  integration/         要求と結果、キャンセル、状態遷移
  browser/             ラベルで操作する主要利用フロー
  reference/           独立した参照実装・過去データとの比較
tools/
  benchmarks/          現行の性能測定
  reference/           Python生成器など
docs/
  architecture.md     現在の構造と読み順
  algorithms.md       導出、精度、計算量
  decisions/          現在も有効な判断
  archive/            参照時だけ読む履歴
```

この構成への一括移動が必要という意味ではない。現行の`calculation/`という名前を維持しても、共通型と責務を整理すれば目的を達成できる。`views/Check.vue`のような単なるroute wrapperとfeatureのbarrelを両方維持する必然性も薄く、ページ固有の役割がなければrouterからfeature pageへ直接つなげばよい。

データフローは次の程度まで説明を短くできることを目指す。

```text
フォームのdraft
  → 検証済みrequest
  → 資源計画・latest-wins実行
  → 入力と対応した計算record
  → 表示windowへのprojection
  → サマリー・確率表・グラフ
```

requestと計算recordはimmutableとして扱い、フォームのdraftだけを編集する。表示windowを変えたら、既存結果で足りるかをprojectionが返し、足りないときだけ新しい計算を要求する。計算結果と表示データを両方多数の場所で保存しない。大きい不変データのVue状態には浅いリアクティビティも選択肢だが、現行の凍結recordやtyped arrayを無視して「すべて深いProxyで遅い」と断定するべきではない。[Vueの不変データに関する性能指針](https://vuejs.org/guide/best-practices/performance#reduce-reactivity-overhead-for-large-immutable-structures)

キャッシュ・Workerを持つruntimeはapp起動時に組み立て、所有者と破棄責務を明確にする。モジュール読込時のsingletonが直ちに不具合とはいえないが、ゼロからならテストとアプリの依存注入を同じ入口にする。

## 推奨する実施順序

1. 公開の入口を整える。ライセンス方針と報告窓口、READMEの読み順を確定し、名前のない操作とバックトラックのテキスト結果を改善する。
2. 表記を固定するテストを挙動のテストへ置き換える。数値オラクルとWorkerの競合テストを保護し、以後の整理が正当な変更を妨げないようにする。
3. 共通型を一本化し、計算・runtime・Vue UIを実装まで型検査する。共通型を複製させるlint規則を同時に修正する。
4. 計算状態と表示状態の遷移を明示し、初期化と更新を同じ実行経路へ寄せる。UIのdraftと有効な計算条件を区別する。
5. 配列表現、FFT、到達不能分岐、現行benchmarkと履歴実験を整理する。数学的な結果と現在の受理範囲を維持する。
6. 許容範囲の大入力と複数コンボについて、モバイル相当の応答性・実機・複数ブラウザで測定し、必要な箇所だけアルゴリズムやWorker境界を変更する。

最も価値のある現代化は、採用技術を入れ替えることではなく、既存の正確な計算を、少ない契約・明確な状態・目的に沿った画面で扱えるようにすることである。
